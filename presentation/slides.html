The Premise
The problem

A small yard.
Tall buildings.
Not enough sun.

My backyard is 24 × 10 ft. A three-story house on one side, other buildings around, half the back shared with a neighbour. I wanted to make absolute best use of the space. Not plant by vibes, but know exactly which spots get the sun hours each plant actually needs to thrive.

The first ask
The full initial prompt · verbatim

One prompt. Four photos.

April 11, 2026 · initial prompt I'm giving you multiple angles of my backyard which is oriented WSW. In some of the photos are the position of the sun's path in winter and summer. We are planning a garden, and also placement of makeshift solar panels in the backyard. We want to plan out the best location for all the plants. Total space is about 24 ft long by 10 ft wide. There is a fence at back and on one side, and the entire back area is shared without a fence on opposite side. We can only use half that space. So total shared space is 24 × 20 ft but ours is 24 × 10 ft. House is also very tall, about 3 stories tall, and there are some other buildings around. Help us determine where to best plant all the plants for sun/shade coverage, and the panels. We might have like 4/5 panels, but that is secondary. Think carefully about this and provide 2-3 total options. We have peas, beans, cauliflower, broccoli, kale, peppers, tomatoes, cucumber, herbs, and a few others.

Create a react threejs tailwind app to visualize this layout. Think very carefully about the orientation and direction of the sun.
The entire project started from this single message + 4 backyard photos.

Solar geometry

Real sun path

Declination, altitude, and azimuth calculated from day-of-year + hour. Ray-AABB shadow casting against every structure. No external APIs.

Methodology
How I used Claude Code

Plan → execute → iterate.

  • Plan mode first. For anything non-trivial I asked Claude to draft an implementation plan, then approved it before any file was touched.
  • Small, scoped prompts. One feature per prompt. Each prompt read like a product spec, not a code request.
  • Commit after every feature. 16 commits, each one buildable and revertable.
  • Auto-memory for corrections. Mistakes (like the localStorage incident) were written to persistent memory so they wouldn't repeat.

13
Lessons
The incident

I lost every saved config.
Then Claude recovered them.

During a "fresh-load" test, Claude ran localStorage.clear() and nuked three saved garden layouts. I had a Save feature. I had JSON export. Neither was enough.

The save: Claude found the browser's LevelDB backups, parsed them, and wrote a restore snippet. Every config came back. Write your guardrails in CLAUDE.md. Take real backups.

Complacency is the bug. Guardrails are the fix.

Ship list
Shipped

Everything I wanted.

  • Interactive 3D viewport with drag-resize gizmos for beds and structures
  • Solar geometry engine: declination, altitude, azimuth, ray-cast shadows against every wall and fence
  • City picker: pick any of 1000+ global cities, sun path auto-adjusts to your latitude/longitude
  • Multi-instance sun heatmaps with independent bounds, opacity, and modes (peak sun hours, direct sun, total daylight)
  • 30-plant library with pH, spacing & PSH thresholds. Resize a bed and it tells you exactly how many plants fit
  • Smart alert panel: click an alert to focus the bed and auto-flash the sun heatmap
  • Save/load configs with JSON import/export and localStorage persistence
  • Configurable yard orientation, compass rose, measurement overlay, and point-sample sun probe
Every feature from user request to shipped, in a handful of prompts.
15
Takeaways
What I learned

The lesson isn't "AI is fast."

It's that planning is the work now. The best moments of this build were the ones where I sat with a plan before any code got written. Claude executed; I architected.

  • Spec like a PM, not a coder. Describe the user-visible behavior, let Claude pick the implementation.
  • Commit relentlessly. Every feature is a checkpoint. Reverts are free.
  • Write guardrails in CLAUDE.md, even for toys. The difference between "real product" mode and "side project" mode is one file.
  • Let mistakes become rules. Auto-memory turns one-time incidents into permanent guardrails.
